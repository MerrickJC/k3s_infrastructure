# Setup Requirements

`values.yaml` references three secrets. Only one (#2, htpasswd) needs to be created manually (see [docs/kubernetes/sealed-secrets.md](../../../../../../docs/kubernetes/sealed-secrets.md) for information about sealing secrets). The other two (#1, #3) are generated and composed automatically.

## 1. SeaweedFS S3 credentials

Autogenerated based on the file [apps/secrets/generated/zot-s3-credentials.yaml](../../secrets/generated/zot-s3-credentials.yaml) which [apps/secrets-generator](../../secrets-generator) uses to autogenerate the secret in the `secrets` namespace, which is then reflected into the `zot` namespace. Injected as `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars so Zot's S3 storage driver can authenticate to SeaweedFS. The same generated pair is also composed into the `zot` identity using SeaweedFS's own `seaweedfs-s3-config`.

## 2. htpasswd (CLI auth: `docker login` / push / pull)

`config.json`'s `http.auth.htpasswd.path` points at `/secrets/htpasswd/htpasswd`, mounted from this secret's `htpasswd` key. Zot requires bcrypt-hashed entries:

```bash
htpasswd -nbB admin '<a-strong-password>' > /tmp/zot-htpasswd
# repeat -nbB for additional users, appending (>>) to the same file
```

If `htpasswd` isn't available locally, an equivalent bcrypt line can be generated with Python's `bcrypt` package instead:

```bash
python3 -c "import bcrypt; print('admin:' + bcrypt.hashpw(b'<a-strong-password>', bcrypt.gensalt()).decode())" > /tmp/zot-htpasswd
```

Then seal the file's contents as the `htpasswd` key:

```bash
kubectl create secret generic zot-htpasswd \
  --from-file=htpasswd=/tmp/zot-htpasswd \
  -n zot --dry-run=client -o yaml | kubeseal --format yaml > zot-htpasswd.yaml
rm /tmp/zot-htpasswd
```

The `admin` username here must match the value in `values.yaml` under the `config.json` section in the field `http.auth.accessControl.adminPolicy.users`. This is what grants delete rights on top of the `**` repository default policy's read/push/update.

## 3. Dex OIDC credentials file (web UI SSO)

Not created here, see [../../secrets/README.md](../../secrets/README.md). [apps/secrets/generated/dex-zot-client-token.yaml](../../secrets/generated/dex-zot-client-token.yaml) defines an autogenerated `ZOT_DEX_CLIENT_SECRET` and reflects it into the `dex` namespace as `zot-dex-client-secret`.

Zot needs the same value in a different shape since Zot's `config.json` has no `$ENV_VAR` substitution and requires a mounted JSON file (`credentialsFile` -> `zot-oidc-credentials`, `/secrets/oidc/oidc-credentials.json`, `{"clientid": "zot", "clientsecret": "..."}`) instead of a bare env var. `zot-oidc-credentials-job.yaml` in this folder defines a `CronJob` which reads the generated `zot-dex-client-secret` value from the `secrets` namespace and writes it into `zot-oidc-credentials` in the shape Zot expects. It runs every 15 minutes and only updates the `zot-oidc-credentials` when the `zot-dex-client-secret` actually changes.

## Rotating a secret

- #1 (generated, S3) and #3 (generated, OIDC): patch the relevant generated secret (`zot-s3-credentials` or `dex-zot-client-token`) in the `secrets` namespace with `secret-generator.v1.mittwald.de/regenerate: "yes"` (see `apps/secrets/README.md`) and the secret will automatically rotate. After maximum 15 minutes (due to CronJob) all consumers will be updated with the new value.
- #2 (sealed): re-run the sealing command above with the new value and commit the updated file. Reloader picks up the change and restarts the pod automatically (no delay) once the SealedSecret decrypts.
