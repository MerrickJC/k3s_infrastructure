# Setup Requirements

`values.yaml` references three secrets. All three are generated and/or composed automatically, so nothing here needs to be created manually.

## 1. SeaweedFS S3 credentials

Autogenerated based on the file [apps/secrets/generated/zot-s3-credentials.yaml](../../secrets/generated/zot-s3-credentials.yaml) which [apps/secrets-generator](../../secrets-generator) uses to autogenerate the secret in the `secrets` namespace, which is then reflected into the `zot` namespace. Injected as `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars so Zot's S3 storage driver can authenticate to SeaweedFS. The same generated pair is also composed into the `zot` identity using SeaweedFS's own `seaweedfs-s3-config`.

## 2. htpasswd (CLI auth: `docker login` / push / pull)

`config.json`'s `http.auth.htpasswd.path` field points at `/secrets/htpasswd/auth`, mounted from this secret's `auth` key. Zot requires bcrypt-hashed entries, and OIDC login (section 3) covers everyone else, so this is only needed for the single `admin` account used for CLI/API access.

Not created here. `secret-generator` has a purpose-built `basic-auth` type which generates a username, a cleartext password, and the bcrypt-hashed `admin:$2y$...` htpasswd line in one step, no separate hashing job needed. [`apps/secrets/generated/zot-htpasswd.yaml`](../../secrets/generated/zot-htpasswd.yaml) is a plain `Secret` annotated with `secret-generator.v1.mittwald.de/type: basic-auth` and `secret-generator.v1.mittwald.de/basic-auth-username: admin`, generated in the `secrets` namespace and reflected into `zot`. The resulting secret has three keys: `username` (`admin`), `password` (cleartext), and `auth` (the htpasswd line Zot actually mounts).

The `admin` username is fixed (via the `basic-auth-username` annotation) to match `values.yaml`'s `config.json` -> `http.auth.accessControl.adminPolicy.users` and is what grants delete rights on top of the `**` repository default policy's read/push/update.

**To log in as `admin`** (CLI/API access, e.g. `docker login`), retrieve the generated plaintext password:

```bash
kubectl get secret zot-htpasswd -n zot -o jsonpath='{.data.password}' | base64 -d
```

Everyone else should use OIDC (section 3) instead since the `admin` account exists for break-glass/automation access, not day-to-day logins.

## 3. Dex OIDC credentials file (web UI SSO)

Not created here, see [../../secrets/README.md](../../secrets/README.md). [apps/secrets/generated/dex-zot-client-token.yaml](../../secrets/generated/dex-zot-client-token.yaml) defines an autogenerated `ZOT_DEX_CLIENT_SECRET` and reflects it into the `dex` namespace as `zot-dex-client-secret`.

Zot needs the same value in a different shape since Zot's `config.json` has no `$ENV_VAR` substitution and requires a mounted JSON file (`credentialsFile` -> `zot-oidc-credentials`, `/secrets/oidc/oidc-credentials.json`, `{"clientid": "zot", "clientsecret": "..."}`) instead of a bare env var. `zot-oidc-credentials-job.yaml` in this folder defines a `CronJob` which reads the generated `zot-dex-client-secret` value from the `secrets` namespace and writes it into `zot-oidc-credentials` in the shape Zot expects. It runs every 15 minutes and only updates the `zot-oidc-credentials` when the `zot-dex-client-secret` actually changes.

## Rotating a secret

All three are generated, so rotation is the same for all: patch the relevant generated secret (`zot-s3-credentials` for #1, `zot-htpasswd` for #2, `dex-zot-client-token` for #3) in the `secrets` namespace with `secret-generator.v1.mittwald.de/regenerate: "yes"` (see `apps/secrets/README.md`). #1 and #3 take up to 15 minutes to reach Zot (has to wait for the `CronJob` to run) while #2 is picked up by reflector immediately, no CronJob involved. Reloader restarts the pod automatically once the secret Zot actually mounts changes.
