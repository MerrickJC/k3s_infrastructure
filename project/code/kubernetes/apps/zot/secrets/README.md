# Setup Requirements

`values.yaml` references four secrets (plus a fifth, `zot-pull-secret`, that isn't mounted by Zot itself but is built here for other apps to consume). All are generated and/or composed automatically, so nothing here needs to be created manually.

## 1. SeaweedFS S3 credentials

Autogenerated based on the file [apps/secrets/generated/zot-s3-credentials.yaml](../../secrets/generated/zot-s3-credentials.yaml) which [apps/secrets-generator](../../secrets-generator) uses to autogenerate the secret in the `secrets` namespace, which is then reflected into the `zot` namespace. Injected as `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars so Zot's S3 storage driver can authenticate to SeaweedFS. The same generated pair is also composed into the `zot` identity using SeaweedFS's own `seaweedfs-s3-config`.

## 2. htpasswd (CLI auth: `docker login` / push / pull / node image pulls)

`config.json`'s `http.auth.htpasswd.path` field points at `/secrets/htpasswd/auth`, mounted from the `auth` key of `zot-htpasswd-combined`, not from either individual credential secret directly.

`secret-generator` has a purpose-built `basic-auth` type which generates a username, a cleartext password, and a bcrypt-hashed `<user>:$2y$...` htpasswd line in one step, no separate hashing job needed. This generator can only produces one username per secret, but Zot needs every user in a single mounted file. So there are three source secrets, all generated in the `secrets` namespace with this annotation, and a `CronJob` ([`zot-htpasswd-combiner-job.yaml`](./zot-htpasswd-combiner-job.yaml)) concatenates their `auth` lines into `zot-htpasswd-combined` every 15 minutes (only writing when something actually changed):

- [`apps/secrets/generated/zot-htpasswd.yaml`](../../secrets/generated/zot-htpasswd.yaml): `basic-auth-username: admin`, not reflected anywhere (only read cross-namespace by the combiner job via scoped RBAC). Matches `config.json` -> `accessControl.adminPolicy.users`, granting delete rights on top of the `**` repository default policy's read/push/update.
- [`apps/secrets/generated/zot-puller-htpasswd.yaml`](../../secrets/generated/zot-puller-htpasswd.yaml): `basic-auth-username: puller`, not reflected anywhere (only read cross-namespace by the two builder jobs via scoped RBAC). Restricted to `["read"]` via `config.json` -> `accessControl.repositories."**".policies`, so this credential can only pull images. This is the identity behind `zot-pull-secret` and it exists so a leaked imagePullSecret, or a compromised node/pod, can't push or delete anything.
- [`apps/secrets/generated/zot-pusher-htpasswd.yaml`](../../secrets/generated/zot-pusher-htpasswd.yaml): `basic-auth-username: pusher`, not reflected anywhere (only read cross-namespace by the combiner job via scoped RBAC). Falls under `config.json` -> `accessControl.repositories."**".defaultPolicy` (`read`, `create`, `update`, no `delete`). Used by GitHub Actions (`kube_kleinkram`) to push images. This stands in for `http.auth.bearer` (GitHub's own OIDC token, which would be keyless and short-lived) because zot v2.1.21 breaks `openid.oidc` web login whenever `bearer.oidc` is also configured ([zot#4033](https://github.com/project-zot/zot/issues/4033)). This credential should only be used until a fix is published for Zot's issue, at which point this credential should be removed and the workflow should switch back to `bearer.oidc`.

**To log in as `admin`** (CLI/API access, e.g. `docker login`), retrieve the generated plaintext password:

```bash
kubectl get secret zot-htpasswd -n secrets -o jsonpath='{.data.password}' | base64 -d
```

Everyone else should use OIDC instead since the `admin` account exists for break-glass/automation access, not day-to-day logins. Kubernetes based automated image pulls (such as when an image being deployed is pulled from the private registry) should use `zot-pull-secret`, not `admin`.

## 3. Dex OIDC credentials file (web UI SSO)

Not created here, see [../../secrets/README.md](../../secrets/README.md). [apps/secrets/generated/dex-zot-client-token.yaml](../../secrets/generated/dex-zot-client-token.yaml) defines an autogenerated `ZOT_DEX_CLIENT_SECRET` and reflects it into the `dex` namespace as `zot-dex-client-secret`.

Zot needs the same value in a different shape since Zot's `config.json` has no `$ENV_VAR` substitution and requires a mounted JSON file (`credentialsFile` -> `zot-oidc-credentials`, `/secrets/oidc/oidc-credentials.json`, `{"clientid": "zot", "clientsecret": "..."}`) instead of a bare env var. `zot-oidc-credentials-job.yaml` in this folder defines a `CronJob` which reads the generated `zot-dex-client-secret` value from the `secrets` namespace and writes it into `zot-oidc-credentials` in the shape Zot expects. It runs every 15 minutes and only updates the `zot-oidc-credentials` when the `zot-dex-client-secret` actually changes.

## 4. Pull secret for other namespaces (`zot-pull-secret`)

Not mounted by Zot's own pod - this is a `kubernetes.io/dockerconfigjson` secret other apps attach as an `imagePullSecret` so their pods can pull private images from the registry.

`zot-pull-secret-builder-job.yaml` in this folder defines a `CronJob` which reads the `puller` credential's `username`/`password` from `zot-puller-htpasswd` and runs `kubectl create secret docker-registry` to build it in the correct shape, in the `secrets` namespace, every 15 minutes (only updating if something changed). The Job re-applies `reflector.v1.k8s.emberstack.com/reflection-allowed-namespaces` on every run, so to give a new namespace pull access, add it to that annotation's value in `zot-pull-secret-builder-job.yaml` which reflector then reads and mirrors the secret there automatically. Once reflected, the consuming app just needs:

```yaml
imagePullSecrets:
  - name: zot-pull-secret
```

in its Helm `values.yaml` (or equivalent on its Pod/ServiceAccount spec).

## Rotating a secret

All are generated, so rotation is the same for all: patch the relevant generated secret (`zot-s3-credentials` for #1, `zot-htpasswd`, `zot-puller-htpasswd` or `zot-pusher-htpasswd` for #2, `dex-zot-client-token` for #3) in the `secrets` namespace with `secret-generator.v1.mittwald.de/regenerate: "yes"` (see `apps/secrets/README.md`). All of #1, #2, and #3 now go through a `CronJob` and so take up to 15 minutes to reach Zot. #4 (`zot-pull-secret`) similarly takes up to 15 minutes to pick up a `zot-puller-htpasswd` rotation, plus reflector's own sync time to reach consuming namespaces. Reloader restarts the Zot pod automatically once the secrets it actually mounts change (this is secrets #1-#3 but not #4 since it is consumed by other apps).

Rotating `zot-pusher-htpasswd` also means updating the `REGISTRY_PASSWORD` GitHub Actions secret in the `kube_kleinkram` repository with the new plaintext password.
